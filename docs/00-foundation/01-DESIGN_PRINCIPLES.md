# 设计原则

> 用途说明：规定产品、架构、安全、界面和开发过程中应长期遵守的基本原则，为后续决策提供统一判断标准。
>
> 状态：初稿 / 待评审
>
> 最后更新日期：2026-07-30

## 1. 使用方式

本文件是项目的长期设计基线，适用于产品需求、数据模型、系统架构、界面、模块、测试和发布工作。

当新需求与本文件冲突时，不应直接绕过原则。应先说明冲突、风险和替代方案，并通过架构决策记录保存最终决定。本文件可以演进，但修改必须谨慎并说明原因。

原则优先级如下：

1. 用户数据安全与控制权。
2. 核心任务的正确性和可恢复性。
3. 清晰的模块边界与长期可维护性。
4. 易用性和操作效率。
5. 新功能数量与开发速度。

## 2. 本地优先

- 核心账号管理能力必须能够完全离线运行。
- 保险库数据默认只保存在用户设备上。
- 核心功能不得要求注册远程账号。
- 不默认启用遥测、行为分析或远程日志。
- 如果未来增加联网能力，必须独立说明用途、默认状态、发送内容和关闭方式。
- 网络模块不得绕过核心数据访问接口直接读取明文敏感数据。

## 3. 安全优先

- 安全需求必须在实现前形成威胁模型和安全设计。
- 不自行设计加密算法或未经评审的加密协议。
- 优先采用成熟、公开、维护活跃的安全组件和平台能力。
- 主密码、派生密钥和解密后的敏感数据不得写入日志。
- 敏感字段默认隐藏，显示和复制行为必须给出清晰反馈。
- 保险库锁定后，应尽可能缩短敏感数据在内存中的存留时间。
- 安全失败应当默认拒绝访问，而不是静默降级为不安全模式。
- 对无法完全保证的能力必须说明现实限制，例如剪贴板清除和安全删除。

安全设计未完成评审前，不得把项目描述为“绝对安全”。

## 4. 用户拥有数据控制权

- 用户应知道数据、配置、备份和日志保存在哪里。
- 数据应支持备份、恢复和迁移，避免被应用永久绑定。
- 删除、覆盖、迁移等高风险操作必须提供明确确认和结果反馈。
- 不以隐藏格式、远程服务或账号体系阻止用户带走自己的数据。
- 导出明文敏感信息时必须明确警告风险，且不得静默执行。

## 5. 模块化优先

任何新增功能在接入主程序前，应先明确：

- 模块的单一职责。
- 输入、输出和公开接口。
- 允许依赖与禁止依赖。
- 生命周期和失败行为。
- 数据访问权限。
- 独立测试方式。
- 对现有模块和数据格式的影响。

模块化不等于所有功能都必须成为可动态安装的插件。第一阶段允许使用编译期模块，只要边界清晰、依赖可控、能够独立测试。

## 6. 分层与依赖方向

建议的职责边界为：

- 界面层：展示状态、接收输入、提供反馈。
- 应用层：编排用户操作和用例。
- 领域层：表达网站、账号、字段等业务规则。
- 数据层：负责持久化、查询和迁移。
- 安全层：负责密钥、加密、锁定和敏感数据策略。
- 平台服务层：负责剪贴板、默认浏览器和本地文件等系统能力。

界面不得成为业务规则和安全规则的唯一实现位置。底层也不得反向依赖具体页面或视觉组件。

## 7. 数据模型优先于界面

- 先定义业务对象、关系和约束，再设计数据库表和界面。
- 数据库为领域模型服务，不能只因界面方便而破坏数据语义。
- 界面可以调整或替换，但核心数据不应因此失去兼容性。
- 核心数据模型应保持稳定，但不能假设永远不变；任何变化都必须具备版本和迁移策略。
- 元数据、用户数据和敏感数据应明确区分。

## 8. 通用能力优先

- 不为单一网站硬编码专属业务字段。
- GitHub Token、OpenAI API Key 等信息通过通用自定义字段或模板表达。
- 网站模板可以提高录入效率，但不能成为读取数据的必要条件。
- 功能应围绕可复用概念设计，避免为短期个例污染核心模型。

## 9. 一个网站支持多个账号

- 网站或服务负责保存共享信息，例如名称、主网址和图标。
- 账号负责保存属于某个身份的登录和敏感信息。
- 同一网站可以拥有私人、工作、测试等多个账号。
- 账号之间相互独立，共享的网站信息不应被重复保存。
- 删除网站时必须明确处理其下所有账号，不得造成无提示的数据丢失。

## 10. 自定义字段是一等能力

- 每个账号可以拥有零个或多个自定义字段。
- 字段应具有名称、类型、值、排序和敏感属性。
- 基础字段与自定义字段应尽量使用统一模型，避免两套不可兼容的逻辑。
- 自定义字段应支持复制、显示或隐藏以及必要的输入验证。
- 字段类型必须可演进，未知类型不能导致整条记录无法读取。

## 11. 易用性与模块化并重

- 日常高频操作应尽量在少量步骤内完成。
- 模块边界用于降低内部复杂度，不应机械地转化为更多页面层级。
- 搜索、复制、打开网址和快速编辑等核心操作应保持易发现。
- 危险操作和普通操作应有清晰的视觉区分。
- 界面反馈应告诉用户发生了什么，但不得在提示中泄露敏感值。

## 12. 安全默认值

- 新保险库默认启用完整的安全保护。
- 密码和其他敏感字段默认隐藏。
- 自动锁定和剪贴板清除应提供安全的默认配置。
- 日志默认脱敏。
- 未知网址或无效输入不得在未提示的情况下直接交给系统处理。
- 不允许为了演示或调试而在正式构建中保留固定密钥、默认主密码或绕过解锁的入口。

## 13. 可恢复性优先

- 数据格式变化必须有迁移、验证和失败恢复方案。
- 更新或迁移前应考虑备份。
- 写入关键数据应尽可能使用事务或等价的原子操作。
- 数据损坏和密码错误应区分处理，避免误导用户。
- 备份只有经过恢复验证才算可用。

## 14. 开源与透明

- 重要产品和架构决定应记录原因，而不只记录结果。
- 安全设计应允许社区审查，同时不得公开真实用户数据或密钥。
- 第三方依赖的选择需要考虑许可证、安全历史、维护状态和替换成本。
- 项目许可证未确定前，`LICENSE.md` 只保留待选择说明。
- 贡献流程应保持可理解，并为安全漏洞提供非公开报告方式。

## 15. 文档与测试属于功能的一部分

- 需求、架构、数据和安全变化必须同步更新相关文档。
- 每个模块应有明确验收标准和相应测试。
- 测试数据必须是虚构数据，不得使用真实账号、密码或令牌。
- 无法测试或无法说明失败行为的关键功能，不应被视为完成。
- 文档状态必须真实反映成熟度，不把骨架标记为已完成。

## 16. 简单实现优先

- 第一版优先选择能够验证核心价值的最小方案。
- 不因“未来可能需要”提前实现复杂插件系统、云同步或企业权限。
- 模块接口应为已知需求服务，同时保留合理扩展点。
- 如果两个方案都满足安全和需求，优先选择更容易理解、测试和维护的方案。

## 17. 新功能接入检查

任何新功能进入开发前，应至少回答：

- [ ] 它解决了哪个明确的用户问题？
- [ ] 它属于现有模块还是需要新模块？
- [ ] 它接触哪些敏感数据？
- [ ] 它是否引入网络访问或第三方服务？
- [ ] 它是否改变数据模型或数据库结构？
- [ ] 它如何失败，用户如何恢复？
- [ ] 它是否有验收标准和测试方案？
- [ ] 它是否保持核心离线能力？

## 18. 待决策事项

- [ ] 确定正式的架构决策记录格式。
- [x] MVP 使用编译期模块注册；动态插件仅作为长期候选。
- [ ] 在安全设计完成后确定自动锁定与剪贴板清除默认值。
- [ ] 确定数据导出格式及明文导出的保护措施。
- [ ] 结合技术栈完善具体的分层依赖检查方式。
