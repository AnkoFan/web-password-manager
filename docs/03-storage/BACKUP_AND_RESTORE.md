# 备份与恢复

> 状态：M2.5 用户备份已实现 / M3 迁移前快照已实现
>
> 最后更新日期：2026-07-31

## 范围

M2.5 提供同一设备应用数据目录内的版本化备份，用于验证一致性和恢复流程。它不是异地备份、云同步或明文导出。

每个备份目录包含：

```text
backups/<backup-id>/
├─ manifest.json
├─ vault.header.json
└─ vault.db
```

数据库继续由原随机 DEK 和 SQLCipher 加密；安全头只保存 KDF 参数与包装后的 DEK。清单不包含用户业务内容。

## 创建

1. 要求保险库已解锁。
2. 关闭 SQLCipher 连接并进入锁定状态，避免复制活动数据库。
3. 把安全头和数据库复制到 `<backup-id>.creating`。
4. 同步文件并计算 SHA-256。
5. 写入版本、备份 ID、创建时间、schema 版本和两个文件摘要。
6. 将临时目录重命名为最终目录。

无论创建成功或失败，保险库都保持锁定，避免在连接状态不明时继续操作。

## 验证

恢复前依次验证：

- 备份 ID 是有效 UUID，目录名与清单一致。
- 清单大小、格式版本和 schema 版本受支持。
- 安全头和数据库 SHA-256 与清单一致。
- 主密码可以解包 DEK。
- SQLCipher 页面完整性、SQLite 逻辑完整性、保险库标记和单一 `vault_meta` 均通过。

## 恢复与回滚

恢复只允许在锁定状态执行。备份先复制到恢复暂存文件并再次打开验证；随后为当前安全头和数据库创建回滚副本，再替换正式文件。替换后再次解锁验证，失败则恢复回滚副本。成功后应用直接进入已解锁状态。

损坏备份或错误密码在替换当前文件前即被拒绝。自动化测试确认这种失败不会改变当前保险库。

## 限制

- 当前备份保存在同一设备，不能防止磁盘整体损坏、勒索软件或设备丢失。
- 安全头与数据库是两个文件，无法获得真正的双文件原子替换；进程在替换窗口内被强制终止时可能留下回滚文件，需要后续恢复工具处理。
- 备份继续使用创建时的主密码和数据密钥；M2.5 不提供备份独立密码。
- 未实现自动轮换、保留策略、用户选择目录或可移动介质导出。

## M3 迁移前快照

安全头 v1 或旧数据库 schema 在首次迁移前，会在应用私有目录的 `migration-backups/<operation-id>/` 创建独立加密快照：

```text
migration-backups/<operation-id>/
├─ migration-manifest.json
├─ vault.header.json
└─ vault.db
```

正式文件只有在头、数据库、长度、SHA-256 和清单全部同步并复核后才允许修改。迁移快照保存原始格式，不会在创建时改写为 v2；它是降级或迁移失败的恢复证据，不是明文导出。

schema 迁移使用 SQLCipher 数据库事务。v2 头先写入独立暂存文件，重读并验证能够解包同一 DEK、匹配数据库 vault ID 后才替换正式头。替换窗口保留唯一回滚头；下次启动可恢复中断的重命名。

迁移快照当前不会自动轮换。M3.5 必须验证升级、恢复和用户可理解的清理流程。

## 验收

- [x] 备份文件保持 SQLCipher 加密。
- [x] 正确主密码可以验证和恢复。
- [x] 错误主密码和摘要不匹配被拒绝。
- [x] 恢复到备份时点的数据状态。
- [x] 损坏备份不会覆盖当前保险库。
- [x] 备份列表不包含业务秘密。
